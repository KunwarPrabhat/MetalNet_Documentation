About MetalNet

MetalNet is a blazing fast, highly efficient, header-only custom Convolutional Neural Network (CNN) library implemented in pure C++20. It aims to provide raw CPU performance capable of matching or exceeding frameworks over optimized CPU regimes, utilizing native vector expressions and robust threading models.

Architecture Overview

The core philosophy of MetalNet surrounds the concepts of Zero-Overhead abstractions and Native Hardware Mapping. Everything from the Directed Acyclic Graph (DAG) construction to deep layer fusions is engineered to exploit modern CPU caches effectively.

  • No External Dependencies: It is standalone, leveraging modern C++ standard templates alongside OpenMP and AVX2 intrinsics.
  • Fluent Graph Builder: Offers an incredibly fluent sequence builder allowing code like model << conv2d(1, 64, 3) << relu();
  • Flexible Extensibility: A polymorphic Layer interface making it trivially easy to add new operations or mathematical transformations while remaining plugged into the automatic differentiation mechanics.

How to Use

Using MetalNet mirrors high-level structures from Keras or PyTorch while retaining C++ execution profiles.

Building a Model Example

#include "MetalNet/MetalNet.h"

using namespace MetalNet;

Model build_vgg_model() {
    Model model;
    // Utilize the fluent API to sequence layers
    model << conv2d(1, 64, 3, 1, 1) << batchnorm2d(64) << leaky_relu(0.01f)
          << conv2d(64, 64, 3, 1, 1) << batchnorm2d(64) << leaky_relu(0.01f)
          << maxpool2d(2, 2) 
          << flatten() << dense(128 * 7 * 7, 10);
          
    // The graph automatically builds internal input/output nodes
    model.compile({128, 1, 28, 28}); // batch_size, channels, H, W
    return model;
}

Inference Example

Model inf_model = build_vgg_model();
inf_model.eval(); // Autonomously drops memory buffers to theoretical minimum

Tensor single_img(1, 1, 28, 28);
// ... load image data ...

Tensor prediction = inf_model.forward(single_img);

How to Compile and Run

Because MetalNet leverages highly specific CPU registers and threading paths, the compilation flags must strictly enforce optimization ceilings.

Step 1: Clone the repository to your local workspace.

git clone https://github.com/KunwarPrabhat/CustomCNN
cd CustomCNN

Step 2: Modify main.cpp as desired for your benchmark script or testing environment.

Compilation Syntax

To compile the project with GCC/G++, invoke the following instruction chain from your terminal. It explicitly maps AVX2 layout pipelines, enables OpenMP scheduling arrays, enforces strict Standard C++20 compliance, and removes unmathematical constraints via fast-math.

g++ -std=c++20 -O3 -mavx2 -mfma -fopenmp -march=native -ffast-math -I./include main.cpp -o benchmark.exe -lpsapi

Run the executable with ./benchmark.exe.

Optimization Techniques Used

Implementation of Directed Acyclic Graph (DAG)

Gradients propagate through an internal DAG layout mapped dynamically via Layer* output_nodes and input_nodes lists. This design safely models non-sequential topologies like Residual Connections natively without tracking external backprop indices. Compilation steps traverse the DAG hierarchically to pre-allocate exact graph tensors.

Zero Allocation Techniques

The library features a strictly Zero-Allocation Hot-Path. The compile() method creates thread-local gradient buffers and dynamically sizes the graph prior to loop execution. Further, a custom C++ `std::allocator` (NoInitAllocator) bypasses the OS 200ms default zero-initialization trap of `std::vector::resize()`, executing tensor allocation under ~1ms. When moving to inference via model.eval(), MetalNet actively triggers memory shrinkage on gradients down to a completely flat footprint.

Vectorization (AVX2 & FMA)

A major throughput breakthrough came via completely circumventing C++ array iterations. `_mm256_fmadd_ps` and `_mm256_loadu_ps` unaligned intrinsic expressions manually instruct the SIMD processor lines. MetalNet processes 8 floats per cycle natively. Fused Multiply-Add (FMA) mathematically folds arithmetic into singular pipeline pulses without precision degradation.

Advanced Multithreading

Loop-collapsed threading arrays orchestrate scaling via `#pragma omp parallel for schedule(static)`. MetalNet actively dodges the "OpenMP Threading Tax" by gating OpenMP directives entirely for latency-sensitive workloads like single-sample inference (batch size 1). When processing batches, OpenMP spreads independent image patches natively over Logical Threads.

Efficient Matrix Multiplication (GEMM)

MetalNet pivoted heavily from slow, naïve nested 6D direct convolutions. To map to modern hardware effectively, Im2Col (Image-to-Column) algorithms are used alongside highly refined Block GEMM dense structures to transform the Convolution routine into heavily parallelized matrix multiplications. To avoid memory bloats to 10GB+, subsequent paths utilize Implicit GEMM paradigms that load patch memory dynamically to subvert memory duplication.

L1/L2 Cache Optimizations

Register Accumulation ensures sums are computed internally via strict `__m256` accumulators and only stored back to RAM memory exactly once. This removes millions of Read-After-Write (RAW) cache hazards occurring in the L1 pipeline. Standard arrays are loop-tiled in sizes matching L2 cache envelopes (`BLOCK_SIZE = 64`) maximizing data permanence per thread computation.

Problems Faced & Bottlenecks

Architectural & Implementation Bottlenecks

Naive Convolution Overhead

The initial implementation used a direct 6-nested-loop convolution, which caused excessive memory traffic and cache thrashing compared to optimized Im2Col or GEMM-based approaches.

Layer Fragmentation

Fragmented layer definitions (Conv → BN → ReLU) created multiple intermediate buffers, leading to significant memory bloat and preventing operational fusion. We resolved this via `FusedConvBNReLU` layers.

OpenMP Threading Tax

Small batch sizes (e.g., Batch 1) suffered from a "threading tax" where the overhead of managing a thread team exceeded the time saved by parallel math, negatively impacting real-time latency.

Hyper-Threading AVX2 Penalty

Using 16 logical threads on an 8-core CPU led to resource contention in the 256-bit AVX registers, causing a performance regression at high thread counts.

Algorithmic Shift (Spatial to GEMM)

Initial versions used a slow spatial sliding-window approach that caused heavy "Cache Thrashing". Transitioning to an im2col (Image to Column) strategy transformed convolutions into a standard Matrix Multiplication (GEMM) problem. However, while im2col improved speed, it physically duplicated image pixels, causing RAM usage to explode to 10.1 GB. We overhauled the architecture to use Implicit GEMM (Direct Convolution), which fetches pixels directly from the original tensor on-the-fly, eliminating intermediate buffers and massive memory expansion.

Memory Management Challenges

The "Ghost" Memory Trap

Every Tensor automatically allocated a .grad array of the same size as its pixel .data, doubling the RAM footprint even during inference-only tasks.

Static Buffer Persistence

The engine initially allocated all backward-pass gradient buffers during compilation, even when the model was in eval() mode.

OS Allocation Latency

Relying on std::vector::resize(sz, 0.0f) forced the operating system to zero-initialize gigabytes of RAM during model setup, leading to a ~200ms initialization gap.

Zero-Allocation and the Malloc Lock

Performance was degraded by dynamic memory allocations inside OpenMP parallel blocks, leading to a "Malloc Lock" where threads stalled waiting for the OS. Implemented a Zero-Allocation hot-path via buffer pre-allocation during the compile phase.

Dataset Retention

Loading the full MNIST/CIFAR dataset into memory and keeping it active alongside training subsets caused an unnecessary ~400MB baseline RAM bloat.

Mathematical & Convergence Issues

AVX Vectorization Inefficiency & Branchless Pass

Using standard if statements inside spatial loops (like MaxPool) prevented the compiler from generating efficient SIMD instructions; checking padding boundaries inside hot loops destroyed the CPU's branch predictor, breaking the 1,000 img/sec barrier. This was resolved by switching to std::max and using branchless fast-paths.

Accumulation Precision & L1 Cache RAW Hazards

Frequent reading and writing to RAM during convolution accumulation risked tiny rounding truncations and massive L1 RAW hazards. This was mitigated by switching to strict in-register accumulation holding intermediate sums entirely within 256-bit AVX2 registers (__m256) via _mm256_fmadd_ps.

Dataset Format Ambiguity

Differences in CSV structures between MNIST (Label in Col 0) and CIFAR (Label in last column) led to out-of-bounds index errors during benchmarking.

Numerical Stability and Denormal Handling

Resolved "Exploding Gradients" that collapsed accuracy to 10% by ensuring zero_grad() calls cleared accumulators. "Denormal" Subnormal floating-point numbers caused significant CPU pipeline stalls, requiring the enabling of "Flush-to-Zero" (FTZ) and "Denormals-are-Zero" (DAZ) hardware modes.

System & Hardware Bottlenecks

AVX2 Stability via Unaligned Intrinsics

Standard C++ std::vector containers do not guarantee the 32-byte alignment required for the fastest AVX2 instructions. To prevent segmentation faults or slow scalar fallbacks, the engine was pivoted to Unaligned Intrinsics (_mm256_loadu_ps).

Eliminating OS Benchmarking Illusions

High RAM readings (e.g., 1.9 GB) were discovered to be a Windows Heap Manager artifact caused by hoarding "freed" memory during repeated model re-builds. By restructuring the benchmark and pinning threads to physical cores, the engine's true, ultra-lean sub-400MB footprint was revealed.

Compiler Optimization Gaps & Thread Affinity

Achieving peak performance required specific flags and lack of explicit thread binding caused context switching and L1 cache misses, requiring OMP_PLACES and OMP_PROC_BIND configurations to stabilize throughput.
